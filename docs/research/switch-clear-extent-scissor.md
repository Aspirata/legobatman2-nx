# Первый контроль по независимому разбору: границы draw и переносы EDRAM

Дата: 2026-11-16. Исследование возобновлено по поручению пользователя после
[разбора Astra](switch-rendering-second-opinion.md). Первый вариант установлен
на Switch и проверен полным обратным чтением. **Run041 выполнен: заметного
выигрыша нет; переключатель не принят как оптимизация.** Далее подготовлена
[последовательная трассировка clear/ownership](switch-clear-causal-trace.md).

## Рассмотренные направления

| Направление | Что подтверждено кодом | Порядок проверки |
| --- | --- | --- |
| Перенос перед draw, который очищает поверхность | Обычный `RenderTargetCache::Update` вызывает `ChangeOwnership` без cutout. Отдельный resolve-clear умеет исключать перезаписываемый прямоугольник. Трёх вершин и известного VS недостаточно, чтобы доказать полную очистку всех аспектов. | Наибольший потенциал; перед исключением переносов нужны точные границы, маски, чтения и последовательность draw. |
| Завышенная оценка области unclipped draw со scissor | В `DrawExtentEstimator::EstimateMaxY` точная интерпретация VS по умолчанию пропускается при ограниченном scissor. Основной переключатель приложение уже включает; `execute_unclipped_draw_vs_on_cpu_with_scissor` по умолчанию выключен. Не доказано, что пропуск затрагивает дорогие проходы текущего пролёта. | Первый отдельный контроль: существующий переключатель, без изменения алгоритма переноса. |
| Восемь переносов stencil до первого настоящего использования | Vulkan cache выбирает bit-pass по depth-типу назначения и отсутствию stencil export. Не проверяет stencil следующего draw. Это сохраняет корректность будущих чтений. | После границ и clear-трассы. Понадобится отслеживание актуальности аспектов; просто отключать stencil при `stencil_enable=false` нельзя. |
| Фиксированные проходы 960×960 | Перехват разрешения меняет только пять полноэкранных allocations. Остальные размеры сохраняются. Назначение конкретной поверхности размером 960×960 ещё не установлено. | Отдельно измерить законченные группы и их потребителей. Изменение размера может ухудшать качество и требует согласовать адресацию, viewport и sampling. |
| Синхронный memexport | Full path создаёт dedicated allocation, копирует ranges, ждёт очередь, отображает память и освобождает ресурсы на каждом вызове. Приложение сохраняет этот путь из-за прежней ошибки геометрии в fast path. | После первых двух контролей: измерение затрат allocation/map, затем пул с прежней синхронизацией. Отложенное чтение требует доказать зависимости guest CPU. |

Повторные FIFO/ZCULL/FSI/timestamp-off/stencil-ones пробы без новых данных
не выбраны. Ни одно из пяти направлений пока не объясняет всё время кадра.

## Почему начат именно этот контроль

Пункты 1 и 2 проверяют общий механизм: лишнее восстановление EDRAM. Включение
существующей оценки по вершинам — малое обратимое изменение перед разработкой
распознавания clear. Если границы уже достаточно точны, выигрыш может отсутствовать;
интерпретация дополнительных VS также может увеличить нагрузку CPU.

Этот контроль проверяет полезность более точной оценки в целом. Он **не заменяет**
причинную трассу `raw state → extent → ownership → consumer` и сам по себе
не доказывает ни конкретный избыточный clear-transfer, ни безопасность его удаления.
Перед изменением `ChangeOwnership` такая трасса остаётся обязательным следующим шагом.

## Исходное состояние и изоляция

С консоли сохранены и проверены прежние NRO/TOML с SHA256
`d45e2d4b841ea75fc297cb10eca56d19a74b38dadf6f19e2f013f30b43652f33` и
`ff18f5a6e7b3ec5b95a0b5df521809633a74d799032ba9b2df74d2674b88656a`.
Это предыдущая same-origin проба, о которой пользователь сообщил возможные
новые артефакты. Её изображение не принято за baseline.

Также получен ранее не собранный здесь `legobatman2_040.log`: ключ `40040102`
присутствует, то есть специализация действительно активировалась. Первые шесть
полных окон после стартового дают 4,639 FPS против 4,176 у run039. Это только
описательное сравнение: одинаковая последовательность сцены и корректность
изображения не проверены; конец run040 обрывается посреди строки. Принимать
same-origin как подтверждённое улучшение по этим данным нельзя.

Для первого контроля восстановлен **точный NRO run039**, а не новая сборка с
подозрительной пробой. Конфигурация семантически отличается от run039 ровно одним
корневым параметром:

```toml
execute_unclipped_draw_vs_on_cpu_with_scissor = true
```

848×480, FBO, direct-color resolve, dump/transfer pitch specialization,
no-effect-point elision, GPU log filtering и выключенные GPU timestamps сохранены.
Проверены наличие имени cvar в baseline NRO и отсутствие его переопределения
в startup. Прежний безопасный full memexport path сохранён. Исходники renderer,
патчи SDK, кэши и сохранения в этом эксперименте не изменялись.

Конфигурация: `config/switch-480p-extent-scissor.toml`.
Она намеренно отдельная: обычная конфигурация сборочного пакета не изменена.

## Следующий запуск

Этот раздел описывает протокол выполненного run041; результаты приведены ниже.

Выйти из USB/MTP, запустить обычный `legobatman2.nro` через hbmenu в режиме
приложения. Оставить начальный пролёт примерно на 90 секунд без управления и
загрузки сохранения; отметить отличия изображения. Затем закрыть игру и снова
подключить MTP. Ожидаемый лог — `legobatman2_041.log`, но номер нужно проверить.

Сравнивать с run039: кадры/секунда на сопоставимых участках, количество
color/depth/stencil transfer draws на guest frame, ожидания очереди, memexport,
паузы компиляции и изображение. Вложенные интервалы не складывать.
При регрессии вернуть точный TOML run039 из
`work/analysis/transfer-same-origin/delivery/before/`; NRO уже baseline.

Если прироста нет, этот широкий переключатель не сохранять как оптимизацию.
Снять ограниченную последовательную трассу границ и ownership для VS
`1E6883FCCDE1F688` и следующих потребителей, прежде чем менять переносы перед clear.

## Результат run041 — разобран 2026-11-17

С консоли получены журнал и полные NRO/TOML. Их SHA256 совпадают с установленным
контролем: действительно выполнялся run039 NRO с единственным новым параметром,
а не оставшаяся same-origin сборка. GPU errors и critical в журнале не обнаружены;
сообщение `ResolvePath(update:\\) failed` существовало ранее и не является новым
сбоем эксперимента. Отдельного подтверждения качества изображения от пользователя
нет; отсутствие ошибок в журнале его не заменяет.

Первые шесть десятисекундных окон после стартового:

| Показатель | Run039 | Run041 |
| --- | ---: | ---: |
| Guest frames / время | 254 / 60,83 с | 257 / 61,16 с |
| FPS | 4,1756 | 4,2021 |
| Color transfer draws / frame | 28,0315 | 28,0467 |
| Depth transfer draws / frame | 48,9685 | 48,9144 |
| Stencil-bit transfer draws / frame | 391,7480 | 391,3152 |
| Queue-submit CPU scope, мс / с | 740,06 | 741,81 |
| Memexport CPU scope, мс / с | 41,42 | 42,58 |

Разница FPS +0,64% при почти неизменной работе переносов и ожидании очереди не
подтверждает полезное ускорение по одному запуску. Повторяющийся профиль окон
также близок к baseline: 4,216 / 3,945 / 4,318 / 3,247 / 4,167 / 5,357 FPS.
Вложенные CPU scopes не складывались.

Вывод ограничен этим контролем: широкое включение интерпретации VS со scissor
не дало заметного выигрыша. Это не доказывает точность каждой отдельной оценки.
Переключатель убирается из следующей конфигурации. Следующий эксперимент сохраняет
исходную оценку и фиксирует raw scissor, реальные вызовы интерпретатора и transfers.

Доказательства: `work/analysis/clear-extent-scissor/hardware/`,
`compare.py`, `comparison-039-041.json`.
