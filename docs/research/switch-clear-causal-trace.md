# Последовательная трасса draw-clear и EDRAM ownership

2026-11-17. Диагностический шаг после [run041](switch-clear-extent-scissor.md):
широкая интерпретация VS со scissor дала 4,202 против 4,176 FPS и почти не
изменила число переносов. Цель — проверить пункт 1
[независимого разбора](switch-rendering-second-opinion.md) на конкретной
последовательности операций. Run042 получен: оба кадра сохранены полностью, без
overflow. По его результатам подготовлена [проба исключения восстановлений перед
полной очисткой](switch-depth-clear-cutout.md).

## Что записывается

Опциональный init-only параметр `lb2_clear_trace=true` включает захват GPU-thread
кадров 180 и 280. Это номера кадров Vulkan command processor, а не номер
десятисекундного отчёта. В остальные кадры буфер не заполняется.

Каждый вызов IssueDraw, включая copy/resolve, получает последовательный ID.
Трасса соединяет:

- Исходные raster/viewport/draw/copy регистры 0x2000–0x23FF: полный первый
  снимок и последующие изменения. Это исходный scissor до обрезки по pitch.
- Идентичности эффективных VS/PS; для известного clear VS `1E6883FCCDE1F688` —
  сами программы и shader constants/fetch/bool/loop registers 0x4000–0x4927.
- Реальное выполнение интерпретатора: индексы вершин и экспортированные значения
  с write masks, включая X/Y/Z/W. Дополнительный запуск VS ради диагностики
  не выполняется. Отсутствие экспортов нужно интерпретировать вместе с raw state
  и событием extent, а не считать нулевыми координатами.
- Результат оценки maxY, height_used, pitch, MSAA и используемые RT/masks.
- Запросы ownership, предыдущих владельцев диапазонов, наличие cutout,
  подготовленные прямоугольники и фактически отправленные transfer draws.
  У transfer также сохраняются дополнительный host-depth source и layout flags,
  различающие чтение отдельного изображения и EDRAM host-depth buffer.
- Фактически отправленный гостевой draw и его effective scissor; resolve result
  и источники/диапазоны dump помогают проследить последующих потребителей.
- Used-texture mask и исходные шесть dwords каждого используемого texture fetch
  перед RequestTextures, включая чтения, которые обслуживает кэш.
- Уже вычисленный ResolveInfo: фактические packed coordinates, размеры,
  destination base/byte range, source EDRAM layout и clear values. Исходные шесть
  guest vertex floats для resolve повторно не считываются.

Трасса хранит не больше 4 MiB payload на кадр в памяти и сохраняется одним блоком
при закрытии кадра. Overflow сохраняет только целый непрерывный префикс и явно
увеличивает `dropped`; неполный захват нельзя выдавать за полную историю кадра.
Запись на SD может добавить краткую CPU-паузу, поэтому этот запуск предназначен
для выяснения зависимостей, а не измерения малого изменения FPS.

Новые GPU queries, fence waits, queue drains или исключения draw не добавлялись.
Существующие решения об ownership, clear, stencil и memexport сохранены.
GPU timestamp hooks собраны как прежде, но runtime-параметр остаётся false.
Scissor-контроль run041 и same-origin не включены. От run039 конфигурация
семантически отличается только включением трассы.

## Проверки и файлы

`tools/test-switch-clear-trace.py` проверяет реальный ограниченный recorder:
выключенный путь, ID и точные payloads, границы размера, overflow без разрыва
записей, завершение кадра и раздельные захваты. Затем проверяет декодер на его
реальном бинарном результате и отклонении повреждённых/усечённых данных.

Сборка ARM64 и обязательные существующие регрессии прошли. Новые SDK hooks
находятся в `port/rexglue-horizon-clear-trace.patch`; обратная применимость к
текущему SDK проверена. Исходные четыре файла сохранены под
`work/analysis/clear-causal-trace/before-sdk/`.

Материалы эксперимента: `work/analysis/clear-causal-trace/`. Контрольный журнал
run041 остаётся в `work/analysis/clear-extent-scissor/hardware/`.

Проверка кода выявила две недостающие зависимости — дополнительный host-depth
source и вычисленные диапазоны назначения resolve. Обе добавлены и повторно
проверены; существенных замечаний по текущим изменениям не осталось.
Финальный build и проверки: `build-verified.log`.

Установлены обычные `switch/legobatman2/legobatman2.nro` и `legobatman2.toml`.
Предыдущая пара полностью сохранена в `preinstall/` и проверена до замены.

библиотеки и установленные программы не изменялись. Новая host-проверка подавляет
системные окна loader error, чтобы ошибка возвращалась в журнал.

## Запуск и чтение

Запустить обычный NRO через hbmenu в режиме приложения. Оставить начальный пролёт
на 90 секунд без управления, затем закрыть игру и подключить MTP. Должны появиться
в журнале строки `LB2 clear trace: frame=180/280 saved=true` и два файла:

```
switch/legobatman2/logs/lb2-clear-trace-180.bin
switch/legobatman2/logs/lb2-clear-trace-280.bin
```

Проверить идентичность установленного NRO/config и связать оба сохранения с новым
журналом, не считать старые файлы свидетельством нового захвата.

После сбора:

```powershell
python tools/read-switch-clear-trace.py <trace.bin> --output <ordered-evidence.json>
```

Сначала проверить `complete`, `dropped`, IDs и сохранение обеих рамок. Затем
выделить clear-кандидаты и связать координаты/мasks с preceding transfers и
следующими чтениями/перезаписями тех же EDRAM ranges. Один shader hash, прямоугольник
либо отсутствие stencil test у следующего draw не доказывают ненужность переноса.
